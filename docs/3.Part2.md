# Late Materialization

In the base solution, the program would materialize all elements of the table, including columns we did not need for the join to work, before executing the join. This is called **early materialization**, and it causes the join pipeline to do a lot of unnecessary copies. This is especially bad when these are string types, which can be very long and in our case never play any part in the joins.

For this reason, we were tasked to change this approach to one which materializes the data that is not needed in the join at the moment we need them—in our case, before returning from the execute function.

### The `value_t` Struct
To achieve this, I needed to find a way to know where I should retrieve the records from when I need to materialize them. For this, I used a struct called `value_t`, which doubles as:
1.  An index to where the strings are inside the tables we are performing a join on.
2.  A materialized `INT32`.

Materializing integers beforehand actually saves us time. Since the struct is 64-bits, we are not performing unnecessary copies of large objects like we did for strings, and all the keys we need for the join are ready when we need them, saving us the time of fetching them every time we need them.

To successfully index the strings, we needed 4 fields:
* **Table Index:** Tells us which table from the plan holds the desired value.
* **Column Index:** The column index.
* **Page Index:** The page index inside the column.
* **Starting Position:** The starting position of the string inside the page.

This struct can index any type of data with minor modifications to the underlying code, but since all joins are performed on `INT32` and `VARCHAR`, we don't account for those types of data. To find the indexes, we simply followed the ideology of the base solution's scan and modified it to store indexes instead of the actual data.

### Representing Integers and Null Values
The main problem in this indexed value way of representing strings was to differentiate between a null value, an `INT32` value, and an index to a string.

We noticed that, since the size of the page was only $2^{13}$ bytes long (or 8192 bytes), we only needed 13 bits to index all data that could possibly fit inside a page. This meant that every data index value greater than $2^{13}$ could be used as a special code.

So we used special values to mark the type of the `value_t` object, resolving the issue we previously had:
* **0xFFFF:** Represents NULL values.
* **0xFFFE:** Represents integer values.

Since we couldn't represent the values in one field, we chose to store the 16 higher-order bits inside the **column index** field and the lower 16 bits in the **table index** field. We did not choose these 2 fields for any particular reason; any 2 fields except data index would have sufficed.

### Design Decisions
**Why did we represent `value_t` this way?**
We could have represented the `value_t` object as a single 64-bit integer, which would have given us the flexibility to give more bits to fields that were not covered by the 16 bits of their respective indexing field, but that was not needed and we chose to keep this design for simplicity.

### Changes in Join Pipeline
Not many changes were needed to the join pipeline for it to work with this new representation. We already established that strings were not needed to perform the join, so all we had to do was:
1.  Change the way the program retrieves the keys.
2.  Get rid of the `visit` functions, which need our data to be of type `variant`. Since we were not using this representation anymore, we needed to remove it.

The other thing that changes, which we covered previously, was the scan algorithm, which now stores indexes to `VARCHAR` and stores `INT32` inside the struct.

# Column-Store Execution

In the previous part we focused on late materialization  meaning that instead of copying all column values upfront we keep only the integer keys needed for joins and we fetch all the information at the very end if they are part of the final output.However  the join algorithm was still working on a row-store table structure. This meant that even though we were storing data in a columnar format we were converting it the rows, performing the join and then converting back to Columnartable . The second part changes the logic of row-store to column-store intermediate results , redesigning the join operators so that temporary outputs are stored in **paged columnar structures**. 

### The `column_t` Struct

To achieve the second part of the project we need to create  a new struct called `column_t` that represents a single column in a table .Using a columnar structure for intermediate results saves us time. Since values are stored contiguously inside pages the  joins can iterate over data with fewer cache misses. This design avoids repeated allocations and as a result the keys and values needed for the join are already organized  reducing the cost of probing 

The `column_t` struct has the following  fields  :
* **num_rows:** The total number of rows (values) in this column across all pages    
* **type:** The data type of the column (`INT32` or `VARCHAR`).
* **pages:** A vector of pages where each page stores in the first 2 bytes the number of rows and the next bytes  `value_t` entries

Each page in a `column_t` follows this layout:
* **First 2 bytes:** A `uint16_t` storing the number of `value_t` entries in this page.
* **Remaining bytes:** A contiguous array of `value_t` structs.

This design allows us to store all values for a single column together 

The `column_t` struct also includes two helper methods:
* **insert_value_to_page():** Inserts a `value_t` entry into the column and automatically increases the row number inside the page
* **Constructors:** We also created a constructor that initializes  a new column with zero rows and the given data type (INT32 or VARCHAR)

* **Deconstructors:** Cleans up memory by deleting all dynamically allocated Page objects

* **Move constructor "column_t(column_t&& other)":** Allows efficient transfer of ownership from one column_t to another without copying all pages

* **Move assignment operator "column_t& operator=(column_t&& other)":** Similar to the move constructor but  after initialization and ensures existing pages are cleaned up before copying the data in the new column_t object

### Design Decisions
**Why did we represent `column_t` this way?**

We represented column_t as a column‑oriented structure because it allows values of the same column to be stored together in memory. This design improves cache locality meaning the CPU can access consecutive values more efficiently. Instead of jumping across rows to find the next value of a column  the program can read them directly in sequence which makes the joins  faster.

Another reason for using a vector of pages in this struct is to avoid allocating memory for every single value. Pages act like blocks that can hold many values at once and keeping data organized. This also makes it easier to handle large database since new pages can be added in vector  when needed


### Changes in Join Pipeline

Significant changes were required to make the join algorithm work with column-oriented data:

1. **Scan function modification:** The `scan_column_table()` function takes a `Columnar table ` as an input and returns `vector<column_t>` instead of row-oriented data. First we initialize a result vector with empty column_t objects.Then for every column in the input table we read the value and store it in the result vector.  with It iterates through input table pages and builds output columns by calling `` for each `value_t` entry.If the column is  INT32 we reads the number of rows the integer values and the bitmap that marks which entries are null. Each value is converted into a value_t and inserted into the output column using insert_value_to_page(). If the column is of type VARCHAR we need to check whether the page contains long strings or normal strings and again use the bitmap to decide whether each entry is valid or null.For the strings instead of copying the  data we store an index pointing to the string’s location. After finishing all pages the function updates the row count for each output column and returns the result vector .

2. **Hash table build phase:** The `extract_keys_from_column()` function is part of the join algorithm that builds the hash table from the one side of the join. We iterate through all the  pages of the given column exctracting the join key from the `value_t` entries and insert it in the hash table. We start with a row_idx counter that will  keep track of the current row across pages. For each page we first reads how many rows are stored (num_rows) and then gets a pointer to the array of value_t entries. Each value_t represents either an integer key, a string index or a null value . The function checks if the entry is null (data_idx == 0xFFFF) and skips it .Once the key is computed, the function looks it up in the hash table. If the key is not inside in the hash table we  create a new entry.By the end of the function is ready to be used in the probe phase to find matching rows from the other table

3. **Probe phase :** The `probe_phase()` function finds the matching rows of the other table :
   - **Prefix array precomputation:** Before starting probing we need to  build prefix arrays for all columns in both the left and right tables. The prefix array  is  used to quickly locate the rows inside paged column_t data. Since each column_t stores its values across multiple pages we need a way to map a global row index (like row 275) to the correct page and the local index within that page. The prefix array solves this by storing the starting row index of that page.

   For example we have a column split into three pages: the first page stores 100 rows, the second stores 150 rows, and the third stores 200 rows. When we build the prefix array we record the starting row index of each page. The first page always starts at 0, so prefix[0] = 0. The second page starts right after the first so prefix[1] = 100. After we compute for every page we find that the prefix array is [0, 100, 250]. Now if we want to find row 180 we look at the prefix array and we see that it is between 100 and 250 meaning ans so it belongs to page 2. The local index inside that page is 180 − 100 = 80. This way instead of scanning through every page we can instantly jump to the correct page and row using the prefix array.

   - **Implementation details** 
    Once the prefix arrays are built for both tables the probe phase begins by selecting the probe side. If the join is building from the left then the right table is used as the probe side. and the same for the other way around. The function iterates through each page of the probe column reading the number of rows and the value_t entries stored there. For each entry we check ifthe entry is null and if it is we  skip that row . Otherwise after the join key is reconstructed again we check if the key is in the hash table .If the key exists in the hash table, it means there are one or more matching rows on the build side. The hash table stores all row indexes where that key appeared so in the probe phase we need to loop through each of those indexes and to find the matching one . For every match the function retrieves the required values from both tables using the helper function get_value(). This function uses the prefix arrays we created earlier to quickly locate the correct page and local index .Depending on whether the join is building from the left or right, the function chooses the correct source column and row index to fetch the value. Finally each retrieved value is inserted into the output column using insert_value_to_page(). This ensures that the results are stored in column_t format to then convert the vector into a Columnar table 


4. **Final conversion:** The `convert_column_t_to_columnar()` function converts the `column_t` results into the final `ColumnarTable` format.We begin by initialising the total number of rows based on the number of rows in  the first column. For every column we create a new Column inside the ColumnarTable and we use the `ColumnInserter` helper from the plan.h to insert values .If the column is   INT32 the function reads each page checks whether entries are null or integers and inserts the null value or the integer value. If the column is of type VARCHAR we  check again for nulls and if it os not a null value we materializes the  string from the original source and then we insert it.

### **Introduction:**

The implementation of the new unchained hashtable is based on the research paper provided in the exercise description. The files that were changed/created for this part of the project are: 
* **include/unchained_hashtable.h** <-- Header file for the Hashtable
* **src/unchained_hashtable.cpp** <-- Implementation of the Hashtable functions
* **tests/unchained_hashtable_tests.cpp** <-- Unit Tests
* **src/execute.cpp** <-- Minor changes to support the new HashTable structure


### **Implementation:**

The implementation was based 100% on the paper, and follows it directly. THe structures used are:
* **Tuple:** Stores the <key, hash, value> of an entry, in order to fit in the directory slots. The hash is used so that it does not need to be recalculated.
* **Buffer Array:** Stores the tuples before the build is complete, without any order.
* **Array:** Stores the tuples after the build is complete, in prefix order.
* **Directory:** Stores the 64 bit number corresponding to the correct tuple pointer, as well as a bloom filter.
* **Tags:** Array used for the bloom filter. It contains 2048 16bit numbers, where only 4 bits are set, and is used so that any entry in the hashtable only sets 4 bits of its corresponding bloom filter

The **flow** of the hashtable is pretty simple: 
First, the vectors are added to the buffer storage. After that, the build is finalized by the user. When that happens, since we already know the tuple number, we create the directory based on that, and allocate an extra spot at the start, for the first tuple pointer. Then the next steps are: 
* **Step 1:** For each tuple in the buffer, we find the correct directory slot using its hash, update the tuple count in that slot in the first 48 bits, and the bloom filter using the tags.
* **Step 2:** For each directory slot, instead of the raw slot count, we now use the running count of all previous slots, in order to point to the correct tuple. For example, in slot 3, if the count was 12, we now add to that the count of slots 2 and 1.
* **Step 3:** For each tuple, we sort it in the correct point on the array, using the slots of the directory. At the same time, with each tuple inserted, we update the slot, in order to now show at a pointer after the given tuple.

Lastly, the probe function is used after finalizing, and it returns a vector of values, corresponding to the given key. The could_contain function helps eliminate most unwanted tuples before ever going to the tuple array, from the directory. After the correct slot was found, we traverse the array in a linear fashion, and grab all of the correct values.


### Improvement in Time

Below is a table of the improvement from each big change in code:

| :--- | :--- | :--- |
| **Basic solution** | 149,000 ms | — |
| **Late materialization** | 95,000 ms | 36.24% |
| **Column store** | 35,000 ms | 76.51% |
| **Unchained hashtable** | 26,000 ms | 82.55% |


After switching from early materialization to late materialization, we saw a significant improvement. This is quite big considering we did not optimize anything else about the pipeline, which shows just how much impact in performance the copies of the strings really had.

The column-store approach makes better use of the CPU cache because values from the same column are stored next to each other in memory. This means that when the processor loads one value into the cache the following values are already nearby so they can be accessed quickly without extra fetches. In contrast in the row-store implementation the values of a single column are scatter across different memory locations and separated by other columns data. As a result searching a single column in a row-store requires jumping through memory repeatedly.

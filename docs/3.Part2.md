## Late Materialization
In the base solution the program would materialize all elements of the table, including columns we did not need for the join to work, before executing the join. This is called early materialization, and it causes the join pipeline to do a lot of unecessary copies. This is especially bad when these are string types, which can be very long and in our case never play any part in the joins. For this reason we where tasked to change this approach to one which materializes the data that is not needed in the join at the moment we need them, in our case before returning from the execute function. To achieve this I needed to find a way to know where I should retrieve the records from when I need to materialize them. For this I used a struct called value_t, which doubles as an index to where the strings are inside the tables we are performing a join on, and as a materialized INT32. Materializing integers before hand actually saves as time, since the struct is 64-bits we are not performing unecessary copies of large objects like we did for strings, and all the keys we need for the join are ready when we need them, saving us the time of fetching them every time we need them. To sucessfuly index the strings we needed 4 fields, the table index, which tells us which table from the plan holds the desired value, the column index, the page index inside the column and the starting position of the string inside the page. This struct can index any type of data with minor modifications to the underlying code, but since all joins are performed on INT32 and VARCHAR we don't account for those types of data. To find the indexes, we simply followed the ideology of the base solution's scan and modified it to store indexes instead of the actual data.

### Representing integers and null values
The main problem in this indexed value way of repressenting strings was to differentiate between a null value, an INT32 value and an index to a string.
We noticed that, since the size of the page was only 2^13 bytes long (or 8192 bytes) we only needed 13 bits to index all data that could possibly fit inside a page. This meant that every data index value greater than 2^13 could be used as a special code. So we used the special value 0xFFFF to represent null values and 0xFFFE to represent integer values. This basically marks the type of the value_t object resolving the issue we previously had. Since we couldn't represent the values in one field we chose to store the 16 higher order bits inside column index field and lower 16 bits in the table index field. We did not chose these 2 fields for any particular reason, any 2 fields except data index would have sufficed

### Why did we represent value_t this way

We could have represented the value_t obeject as a single 64-bit integer, which would have given us the flexibility to give more bits to fields that were not covered by the 16 bits of their respective indexing field, but that was not needed and we chose to keep this design for simplicity. 

### Changes in join pipeline

Not many changes were needed to the join pipeline for it to work with this new represantation. We already established that strings were not needed to perform the join so all we had to do was change the way the program retrieves the keys, and get rid of the visit functions, which needs our data to be of type variant, and since we were not using this represantation anymore we needed to remove it.

The other thing that changes which we covered previously was the scan algorithm, which now stores indexes to VARCHAR and stores INT32 inside the struct.

## Top-level join 

At this moment the program still used the to_columnar function which takes a materialized row_store table and converts it to a columnar table. This makes some unecessary copies of strings which take time. So we combined the 2 functions, meaning that we would materialize the table as we were converting to columnar. This saves some copies, but since these copies were only for 1 table, the time saved was not projected to be huge, and indeed in our machine we saw no improvement on time. To combine the 2 functions, we modified the existing to_columnar function to take the unmaterialized table and materialize the strings right before inserting them into the pages of the columnar table we were about to return. 

For now the join was still working on a row-store table structure, which is not ideal.
